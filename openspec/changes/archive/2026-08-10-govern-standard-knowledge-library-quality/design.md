## Context

当前正式内容由 PostgreSQL/Flyway 发布，规范表是权威来源，`ai_standard_library_items` 仅承担兼容快照。V11 已将库扩到 737 个知识节点、188 个能力点、527 个易错点、185/186 个提升点和 130 个场景，但隔离恢复审计发现：358 个 V3 易错点的修正策略仍是元说明；15 组知识节点重名且部分仍为模板描述；两个字符串错因展示名完全相同；V11 的 48 个课堂—竞赛迁移对复用了同一教师动作。

迁移必须兼容两种环境：生产或历史备份中存在完整内容，空数据库只建立 schema 而没有种子内容。工作区同时存在其他任务的未提交改动，本变更不能触碰或提交那些文件。

## Goals / Non-Goals

**Goals:**

- 在不改变稳定 code、父子层级和业务诊断事实的前提下治理存量内容。
- 让旧易错点的修正策略包含可执行步骤、最小复现和验证动作，而不是把责任重新交给 AI。
- 让跨路径同名知识点从名称、描述、别名和 path 上可区分，同时仍可通过原术语召回。
- 让同一迁移对的课堂动作与竞赛动作分别体现形成性检查和约束/评测核验。
- 将本次发现转化为可重复的迁移内保护、发布审计指标和工程回归。

**Non-Goals:**

- 不增加知识节点、能力点、易错点、提升点或场景数量，不为体积指标造新条目。
- 不合并或删除稳定 code，不改写 `submission_diagnosis_facts`、推荐事件等历史业务事实。
- 不建立高中库、竞赛库或工程库的平行知识树，不把标准库变成规则诊断引擎。
- 不改 API、页面或 AI 调用链。

## Decisions

### 1. 采用非破坏式消歧，不做节点物理合并

对 15 组同名节点按其路径语义改名，并同步最后一级 `path`、具体描述、学习目标、典型问题和原词别名。原 `library_version` 继续保存内容来源批次，所有 code、parent_code、type 和关系引用保持不变。

选择这一方案是因为同名记录大多是不同观察面，例如“图输入合同”和“图型题结构识别”，不是可以安全删除的重复概念。物理合并会破坏历史知识路径，并把输入建模、算法方法和工程预算重新混在一起。

### 2. 用“类型协议 + 当前错因事实”重写 358 条旧修正策略

V3 的每条旧易错点已经有唯一名称、症状和误区，只缺修正动作。迁移按 `mistake_type` 选择边界、复杂度、状态、建模、输入输出、调试等 18 类验证协议，并把当前错因名称与症状写入修正步骤。结果必须同时包含：修复前合同或假设、最小复现/首个偏差、修改动作和修复后验证。

这种做法比逐条手工写 358 个风格不一致的段落更可审计，也比单一通用模板更具体。迁移同时将规范内容同步到既有平铺快照的描述、误区、三级提示和证据信号；不会让平铺表反向成为权威来源。

### 3. 保留重叠匹配的两个稳定错因，但重写为不同层次

两个 code 已被不同能力和提升路径引用。V12 不停用任一 code，而是把 V7 条目明确为“未先确认是否允许重叠”的题意/合同错误，把 V8 条目明确为“匹配后按完整模式长度推进”的实现错误，并分别补充修正策略。这样既保护历史引用，也避免 AI 和教师看到两个完全同名条目。

### 4. 只重写 V11 竞赛场景的教师动作

课堂场景继续保留形成性检查；竞赛场景的教师动作改为先核对约束画像与复杂度目标，再要求学生用该场景的唯一可观察证据完成对拍、边界或评测证明。该文本由每条场景已有的 `observable_evidence` 组成，因此与具体主题绑定，并能避免 48 对机械复用。

### 5. 迁移内门禁与发布审计双层保护

V12 末尾使用 SQL 断言：存在标准内容时，目标存量规模必须符合当前基线；迁移后元说明修正策略为 0、治理目标同名为 0、V11 完整迁移对同动作数为 0、平铺快照与规范表一致、历史业务事实计数不变。`check-discipline-data-quality.sh` 增加同样的长期指标，Flyway 集成测试更新为 V1→V12。

空数据库没有标准内容时，迁移以 0 条更新安全通过；生产/历史恢复环境才执行规模与内容断言。

## Risks / Trade-offs

- [批量生成的修正策略仍有共同结构] → 每条都绑定自身名称和症状，并按 18 类错误协议选择不同检查法；门禁同时检查元说明、最短长度和规范/快照同步，不把“字数变长”当成质量完成。
- [改名影响按中文名称搜索的习惯] → 稳定 code 不变，aliases 保留原名与英文/场景词，path 与新名同步；原术语仍可召回。
- [历史备份内容数量与当前生产有轻微差异] → V12 只对本轮明确目标断言，不借机修补无关的旧提升点缺口；业务表计数在迁移前后保持不变。
- [已有两个重叠匹配 code 继续存在] → 通过语义分层消歧而非删除；后续若运行时真正使用 legacy mapping，再单独设计可观测的合并迁移。

## Migration Plan

1. 在隔离 PostgreSQL 恢复库上记录治理前指标与业务事实计数。
2. 执行 V12：知识节点消歧、旧易错点修正策略补实、平铺快照同步、重叠错因分层、竞赛场景动作改写。
3. 执行迁移内断言与 `check-discipline-data-quality.sh`，对比治理前后指标。
4. 运行 V1→V12 空库迁移、重复启动、旧库显式 baseline、Hibernate validate 和迁移安全测试。
5. 迁移失败由 Flyway 事务整体回滚；发布前不手工修改生产库。已成功发布后如需恢复展示文案，必须新增后续迁移，不能修改 V12。

## Open Questions

无。物理合并兼容错因、继续扩容和运行时搜索权重调整均不在本轮范围。
