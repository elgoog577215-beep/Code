## Context

平台是 Spring Boot 3.2、Spring Data JPA、React/Vite 单体应用。当前教师身份是统一口令生成的签名 Cookie，学生身份是浏览器保存的签名 Token；班级、作业和题目没有教师归属。正式环境使用 Postgres，但 Hibernate 仍以 `ddl-auto=update` 改结构。正式内容数据库化变更 `migrate-seeded-content-to-database` 尚未完成，因此本变更必须把它作为发布门禁，不再增加任何运行时内容 seed。

## Goals / Non-Goals

**Goals:**

- 在一个应用和一个数据库内建立强制教师租户边界，不引入学校组织层。
- 让认证、名单、作业目标、题目版本和 AI 额度都可被自动化测试和审计。
- 用向前迁移和迁移前备份保护现有 16 道公共题及历史教学数据。
- 保持代码评测在 AI 不可用或额度不足时可独立工作。

**Non-Goals:**

- 不建设支付、套餐、BYOK、对外 API Token、短信/邮箱认证和学校协作角色。
- 不把班级码描述为高强度实名认证，不承诺抵御班级内部共享身份信息。
- 不实现数据库迁移的自动向下回滚，回滚以已验证备份恢复为准。

## Decisions

### 1. 认证采用 Spring Security 加数据库不透明会话

教师与学生 Cookie 只保存高熵随机令牌，数据库保存 SHA-256 哈希、过期时间和撤销时间。自定义认证过滤器恢复当前主体，Spring Security 负责路径角色、CSRF 与统一拒绝响应。密码使用 BCrypt。相比继续使用自包含 HMAC Token，这一方案能在停用名单、改密或封禁时立即撤销，而无需维护额外黑名单。

浏览器写请求使用 Cookie CSRF Token 与 `X-XSRF-TOKEN`；登录、注册接口仍接受 CSRF 初始化 Cookie。生产 Cookie 强制 `Secure`，开发和测试允许关闭。旧教师 session/logout 路径保留一版别名，但旧统一密码登录仅在显式开发兼容开关下可用。

### 2. 教师归属由服务端主体决定并双层校验

`class_groups.owner_teacher_id` 和 `assignments.owner_teacher_id` 必填，学生通过班级继承。列表仓储以 owner 过滤；任何包含资源 ID 的服务方法再次取当前主体并校验所有权。管理员治理只出现在 `/api/admin/**`，管理员调用普通教学接口时不获得跨租户旁路。

### 3. 名单身份使用“班级 + 学号”，登录增加姓名与班级码核验

加入码以 BCrypt 保存，因为码空间比会话令牌小，单纯快速哈希容易离线枚举。班级创建/轮换只返回一次明文。学生导入以同班学号 upsert，姓名变化更新记录；缺学号历史数据迁移为 `NEEDS_REVIEW`。学生会话每次使用时重新校验名单仍为 `ACTIVE`，从而让停用即时生效。

### 4. 作业目标使用模式字段与接收人关联表

`CLASS` 在查询时动态读取当前有效名单，不保存展开快照；`STUDENTS` 使用唯一约束的 `assignment_recipients`。统一策略服务用于作业列表、题目访问、代码提交和统计，避免各入口产生不一致口径。历史提交不删除，统计响应显式标记非当前名单记录。

### 5. 题目采用追加版本而非原地改变语义

题目行同时作为版本实体，以 `series_id + version_no` 组织。只有所有者的 `PRIVATE/DRAFT` 可原地编辑；审核、发布、修订、提升公共和作业冻结均复制题目及测试用例。任何非草稿版本只读。删除转换为 `ARCHIVED`，历史引用仍能按 ID 读取。该选择会增加行数，但能保证审计和作业可重复性。

### 6. AI 额度采用“预留—调用—结算”事务协议

网关先以 `(teacher_id, month)` 行锁创建/读取额度，再以全局唯一幂等键预留 1 单位。供应商调用在事务外执行；至少一次成功后结算为已用，否则释放预留。每次供应商尝试写 `ai_usage_events`，但同一业务动作只生成一个可计费结果。并发请求通过数据库唯一约束与悲观锁防止超扣。

匿名/公共练习没有教师上下文，网关直接拒绝外部调用并返回本地基础提示。现有 ModelScope 客户端成为 `AiProviderGateway` 的首个适配器，密钥仍只来自服务端环境变量。

### 7. Flyway 以基线脚本和后续迁移接管结构

`V1` 描述当前可部署基线，`V2` 创建身份、归属和会话，`V3` 创建名单/目标，`V4` 创建题库版本，`V5` 创建额度/审计。已有非空库使用 `baseline-on-migrate=true` 和受控基线版本接管后执行 V2+；空库从 V1 开始。生产 `ddl-auto=validate`，测试可使用独立 profile。相比继续依赖 Hibernate update，该方案可审查、可演练且不会因实体加载顺序改变正式结构。

### 8. Bootstrap 管理员是不可登录占位身份

迁移创建固定 UUID、`BOOTSTRAP_REQUIRED`、无可用密码的 ADMIN，并把历史班级/作业及平台题目归属关联到它。启动激活器仅在提供 `BOOTSTRAP_ADMIN_USERNAME` 与 `BOOTSTRAP_ADMIN_PASSWORD` 时设置 BCrypt 并转为 `ACTIVE`；明文不写日志、不返回接口。激活器幂等且不会覆盖已经激活的管理员。

## Risks / Trade-offs

- [现有非空数据库的实际结构可能与实体基线漂移] → 在正式库副本运行 Flyway info/migrate、ORM validate 和数据不变量查询，未通过不得上线。
- [改为 CSRF 后旧前端写请求可能失败] → API 客户端统一读取 XSRF Cookie，浏览器 smoke 覆盖登录、创建、导入和提交。
- [大范围所有权改造遗漏某个分析接口] → 路由目录测试枚举教师接口，并用双教师 IDOR 参数化集成测试覆盖班级、学生、作业、题目、提交和分析。
- [短班级码被暴力尝试] → 使用慢哈希、IP 限流、统一错误和可轮换码；仍明确其课堂级安全边界。
- [AI 预留因进程崩溃滞留] → 预留记录带时间戳，readiness/定时恢复只释放超时且无成功事件的预留。
- [功能面过大影响现有单教师流程] → 按认证/租户、名单/作业、题库、AI、前端顺序切片，每片先写失败测试并保持全量测试可运行。

## Migration Plan

1. 完成或冻结 `migrate-seeded-content-to-database`，导出正式内容数量与代表性查询结果。
2. 对正式 Postgres 执行现有备份脚本并校验备份可读；在空库执行 V1–V5。
3. 在正式库副本执行 baseline、V2–V5、Hibernate validate 和数据不变量检查，演练备份恢复。
4. 维护窗口部署应用，激活首位管理员，确认历史数据归属并修复 `NEEDS_REVIEW` 名单。
5. 启用多教师入口，邀请 3–5 位教师试用；保留旧 session/logout 别名一个版本但关闭统一口令。
6. 若迁移或不变量失败，停止应用并从迁移前备份恢复；不尝试自动逆向 DDL。
